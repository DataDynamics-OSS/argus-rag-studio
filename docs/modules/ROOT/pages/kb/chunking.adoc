= 청킹 처리 가이드

긴 문서를 검색 단위인 *청크* 로 나누는 단계를 자세히 다룹니다. 청크는 임베딩·검색·생성이 모두
공유하는 단위라, 청킹 품질이 곧 검색 정밀도와 답변 품질의 상한이 됩니다.

== 처리 흐름

인제스천 워커가 파싱 결과(본문 텍스트/Markdown)를 받아 다음 순서로 청킹합니다.

[source]
----
파싱 본문
  → (전략별) 문장/블록 분리
  → 그룹화(chunk_size 한도 내, 전략 규칙 적용)
  → 오버랩 부착(스마트 절단) · 품질 가드(예산 캡 · 작은 청크 병합)
  → 청크별 위치 메타데이터(section_path · offset) 계산
  → 임베딩 → pgvector + tsvector 색인
----

청킹은 컬렉션 설정 *전략(`chunk_strategy`)* · *단위(`chunk_unit`)* · *크기(`chunk_size`)* ·
*오버랩(`chunk_overlap`)* 으로 제어합니다. 변경 시 재인덱싱이 필요합니다.

== 전략 (예제 포함)

=== auto — 내용 기반 자동 선택(기본 권장)

파싱 결과에 *표·헤딩이 있으면 `markdown`*, 없으면 *`recursive`* 로 자동 선택합니다. `parse_strategy=auto`
(파일 유형별 파싱)와 짝을 이루면, 한 지식베이스에 여러 형식을 섞어도 *파일마다* 알맞게 청킹됩니다
(표 든 PDF→markdown, 평문 TXT→recursive). `semantic` 은 임베딩 비용이 큰 의도적 선택이라 자동 선택하지 않습니다.

=== recursive — 구조 보존(범용 기본값)

구분자 우선순위(문단 `\n\n` → 줄 `\n` → 문장 `. `·`。` → 공백)로 `chunk_size` 이내가 되도록 자릅니다.
의미 단위(문단·문장)를 최대한 살리는 범용 기본값입니다.

.예: `chunk_size=40`, `overlap=0` (문자)
[source]
----
입력:  "환불 정책입니다. 7일 이내 가능합니다. 영수증 필요합니다. 반품비 고객부담입니다. 교환 가능합니다."

청크0: "환불 정책입니다. 7일 이내 가능합니다. 영수증 필요합니다."   (33자)
청크1: "반품비 고객부담입니다. 교환 가능합니다."                  (22자)
----

=== sentence — 문장 보존(FAQ·QA), 한국어 인식

문장 경계로 나눈 뒤 `chunk_size` 이내로 그리디하게 묶어 *문장이 중간에서 잘리지 않게* 합니다.
문장 분리는 *kss*(설치 시, 한국어 종결어미·약어 정확)를 쓰고, 없으면 약어·소수점을 보호하는
규칙 기반으로 폴백합니다.

.예: 약어·소수점 보호
[source]
----
입력:  "김 박사는 3.14를 좋아한다. 그는 Dr. Kim이라 불린다. 환불은 7일 이내 가능합니다."

단순 분리(과거): "그는 Dr." | "Kim이라 불린다."   ← 약어에서 잘못 끊김
sentence 전략:   "그는 Dr. Kim이라 불린다."          ← 'Dr.'·'3.14' 유지
----

=== paragraph — 문단 보존(산문·보고서)

빈 줄(`\n\n`, 문단 경계)로 나눈 뒤 `chunk_size` 이내로 그리디하게 묶어 *문단이 중간에서 잘리지 않게*
합니다. 문단이 곧 의미 단위인 산문·보고서·공지에 적합합니다. 한 문단이 `chunk_size` 를 넘으면 그
문단만 `recursive` 로 폴백 분할합니다. (`recursive` 도 문단을 1순위 구분자로 쓰지만 크기에 맞춰
여러 문단을 합치거나 자르는 반면, `paragraph` 는 *문단 경계 자체를 보존* 하는 데 무게를 둡니다.)

.예: `chunk_size=40`, `overlap=0` (문자)
[source]
----
입력:  "환불 정책입니다.\n\n7일 이내 가능합니다.\n\n영수증이 필요합니다."

청크0: "환불 정책입니다.\n\n7일 이내 가능합니다."   (문단 경계 보존, 40자 이내로 묶음)
청크1: "영수증이 필요합니다."
----

=== section — 섹션 헤더 보존(매뉴얼·규정·논문)

섹션 *헤더* 를 경계로 자르고, 각 청크에 *상위 섹션 경로(breadcrumb)* 를 `section_path` 메타로 답니다.
`markdown` 이 마크다운 표·헤딩에 특화돼 있다면, `section` 은 *일반 텍스트의 섹션 헤더까지 넓게 인식* 합니다.

* 인식하는 헤더: 마크다운 헤딩(`#`~`######`), setext 밑줄(`===`/`---`),
  번호 헤더(`1.` / `1.2` / `2.3.1`), 키워드 헤더(`Chapter`/`Section`/`Part`/`Appendix`, `제1장`/`제2절`).
* 헤더 깊이로 *섹션 경로* 를 만듭니다(예: `# 1장 개요 > ## 1.1 배경`).
* 작은 섹션은 같은 상위 경로 안에서 묶고, 한 섹션이 `chunk_size` 를 넘으면 헤더를 각 조각에 반복하며 본문을 분할합니다.
* 구조 우선 전략이라(markdown 과 동일) 문자 오버랩은 적용하지 않습니다.

NOTE: 번호 헤더 인식은 휴리스틱이라 `3.14 ...` 처럼 줄 첫머리의 소수점·번호 목록을 헤더로 오인할 수 있습니다.
헤딩이 분명한 매뉴얼·규정·논문에 권장하고, 표 위주 문서에는 `markdown` 을 쓰세요.

.예: `chunk_size=60`, `overlap=0` (문자)
[source]
----
입력:
  # 1장 개요
  개요 본문입니다.
  ## 1.1 배경
  배경 설명 본문입니다.

청크0: "# 1장 개요\n개요 본문입니다."           section_path="# 1장 개요"
청크1: "## 1.1 배경\n배경 설명 본문입니다."      section_path="# 1장 개요 > ## 1.1 배경"
----

=== fixed — 고정 길이 윈도우

구분자를 무시하고 정확히 `chunk_size` 단위로 하드 컷합니다. 균일한 길이가 필요할 때만 쓰며,
문장·단어가 잘릴 수 있습니다. `token` 단위와 함께 쓰면 정확히 N토큰 윈도우로 자릅니다(*Fixed Token Chunking*).

=== markdown — 구조 인식(표·헤딩 보존)

`layout`/`docai`/`vlm` 파서가 만든 Markdown(표·헤딩)과 짝을 이루는 전략입니다.

* *표·코드블록을 원자 단위로 보존* — `chunk_size` 보다 작아도 표를 중간에서 자르지 않습니다.
  (표가 단독으로 크면 헤더를 반복하며 행 단위로 분할)
* *헤딩을 경계* 로 쓰고, 각 청크에 *상위 헤딩 경로(breadcrumb)* 를 덧붙여 소속 섹션을 알 수 있게 합니다.
* 헤딩 컨텍스트로 연속성을 확보하므로 문자 오버랩은 적용하지 않습니다.

.예: `chunk_size=120` 이라도 표는 한 청크에 온전
[source]
----
입력(파서 산출 Markdown):
  # 2026 연간 보고서
  ## 분기 실적
  | 분기 | 매출 | 성장률 |
  | --- | --- | --- |
  | Q1 | 100 | 5% |
  | Q2 | 120 | 20% |

청크: "# 2026 연간 보고서
       ## 분기 실적
       | 분기 | 매출 | 성장률 |
       | --- | --- | --- |
       | Q1 | 100 | 5% |
       | Q2 | 120 | 20% |"        ← 헤딩 경로 + 표 전체가 한 청크에 보존
----

NOTE: 같은 표라도 `recursive`/`fixed` 는 표를 행 중간에서 잘라 헤더와 데이터를 분리하지만,
`markdown` 은 표를 통째로 보존하고 섹션 맥락까지 붙입니다.

=== semantic — 의미 경계 분할

문장을 임베딩해 *인접 문장의 유사도가 급락하는 지점*(주제 전환)을 의미 경계로 잡습니다. 경계 임계는
문서별로 인접 거리의 90 percentile 을 쓰는 *적응형* 이며, `chunk_size` 를 상한으로 지킵니다. 가장
정교하지만 인제스천 시 *문장마다 임베딩*이 필요해 비용·시간이 더 듭니다.

.예: 주제 전환 지점에서 분할 (`chunk_size=500`, 실제 임베딩)
[source]
----
입력: "회사는 2020년 설립. 빠르게 성장. 팀이 우수.
       환불은 7일 이내 가능. 영수증 필요. 배송비 환불 불가.
       비밀번호는 분기마다 변경. 2단계 인증 필수."

청크0: "회사는 2020년 설립. ... 배송비 환불 불가."   ← 회사·환불(의미 인접)
청크1: "비밀번호는 분기마다 변경. 2단계 인증 필수."     ← 보안(주제 전환)
----

== 크기 단위 — char vs token

`chunk_unit` 으로 청크 크기·오버랩을 *문자* 또는 *토큰* 으로 셉니다.

[cols="1,3"]
|===
| `char` (기본) | 글자 수. 간단하지만 언어·코드마다 토큰 환산이 달라 임베딩 한도를 넘길 수 있음.
| `token` | 임베딩 모델이 실제 세는 토큰 수(tiktoken). 토큰 윈도우(보통 512)를 정확히 지킴. 미설치 시 char 폴백.
|===

문자당 토큰 수는 언어에 따라 크게 다릅니다.

[source]
----
"Hello world, this is a test."   → 28자 / 8토큰   (영어 ~0.3 토큰/자)
"안녕하세요 RAG 스튜디오입니다."  → 18자 / 15토큰  (한국어 ~0.8 토큰/자)
----

따라서 한국어·코드가 많고 토큰 한도가 빡빡하면 `token`(예: 크기 512, 오버랩 64)을 권장합니다.
`char` 로 1000자를 잡으면 한국어에서는 약 800토큰이 되어 512 윈도우를 초과할 수 있습니다.

== 오버랩 — 스마트 절단

인접 청크가 경계에서 문맥이 끊기지 않도록, 직전 청크의 꼬리 일부를 다음 청크 앞에 덧붙입니다.
보통 크기의 10~15% 로 둡니다. 꼬리의 *시작을 문장→단어 경계로 스냅* 해, 잘린 부분 단어가 아니라
완결된 문장/단어로 시작하게 합니다.

[source]
----
원시 꼬리:        "면 검색이 됩니다 단어가"      ← 'ㄴ면'에서 잘린 조각
스마트 스냅 후:    "검색이 됩니다 단어가"         ← 단어 경계에서 시작

원시 꼬리:        "환불됩니다. 단어가 달라도"
스마트 스냅 후:    "단어가 달라도"               ← 경계에 인접한 완결 문장만
----

오버랩은 `chunk_size` *안에* 포함됩니다(예산 캡) — base 청크를 `chunk_size - overlap` 으로 잡아
오버랩을 더해도 최종 청크가 `chunk_size` 를 넘지 않습니다. 즉 `chunk_size` 가 진짜 상한입니다.
`markdown`/`semantic` 은 구조·의미로 연속성을 확보하므로 문자 오버랩을 쓰지 않습니다.

== 품질 가드

* *예산 캡* — 위처럼 오버랩을 포함해도 `chunk_size` 를 넘지 않게 합니다.
* *작은 청크 병합* — `chunk_size` 의 10% 미만인 짧은 조각("끝." 등)은 노이즈 벡터가 되지 않도록
  이웃 청크에 병합합니다(단 합쳐도 `chunk_size` 한도 내일 때만).

[source]
----
병합 전: ["… 그리고 더 이어집니다."(33자), "끝."(2자)]
병합 후: ["… 그리고 더 이어집니다. 끝."(36자)]   ← 2자 노이즈 청크 제거
----

== 청크 위치 메타데이터

각 청크는 *문서 내 위치* 를 함께 저장해 인용·하이라이트에 활용합니다.

[cols="1,3"]
|===
| `section_path` | markdown 전략의 헤딩 경로(예: `회사 규정 > 휴가`). 검색 결과·인용에 노출.
| `metadata_json` | `char_start`·`char_end`(원문 문자 offset)·`char_count`·`token_count`.
|===

.예: 검색 결과에 섹션이 함께 표시
[source]
----
저장: section_path="회사 규정 > 휴가",
      metadata_json={"char_start":16,"char_end":72,"char_count":71}

검색 hit: { "text": "연차는 …", "section_path": "회사 규정 > 휴가", ... }
          → "회사 규정 > 휴가" 섹션의 내용으로 인용 가능
----

== 전략·단위 선택 가이드

[cols="2,3"]
|===
| 문서 유형 | 권장 조합

| 표가 많은 PDF·보고서·명세서
| `parse_strategy=layout`(또는 `docai`/`vlm`) + `chunk_strategy=markdown` + `chunk_unit=token`

| 한국어 산문·매뉴얼
| `chunk_strategy=sentence` + `chunk_unit=token`(한국어 토큰 한도 정확)

| FAQ·QA(문장 단위가 곧 답)
| `chunk_strategy=sentence`

| 주제가 여러 개 섞인 긴 문서(정교한 분할 필요·비용 허용)
| `chunk_strategy=semantic`

| 여러 형식이 섞인 지식베이스·잘 모를 때
| `parse_strategy=auto` + `chunk_strategy=auto`(기본 권장) — 파일마다 자동 최적화
|===

TIP: 표가 핵심인 문서는 *파싱(layout/docai/vlm) → 청킹(markdown) → 토큰 사이징* 의 조합이
파싱으로 살린 구조를 청킹·임베딩까지 그대로 전달하는 권장 경로입니다.
